### 模块 A：Upload API Key 体系（后端 `cfcc173`）

**目标**：为 Operator 提供专用的程序化 Upload API Key，实现机器人数据自动上传，彻底脱离浏览器 session 鉴权。

#### A.1 数据库 — 新表 `data_api_keys_upload`

```sql
CREATE TABLE data_api_keys_upload (
    upload_api_key_id BIGSERIAL PRIMARY KEY,
    user_id           BIGINT NOT NULL,
    key_prefix        TEXT NOT NULL,
    key_hash          TEXT NOT NULL UNIQUE,
    status            TEXT NOT NULL DEFAULT 'ACTIVE',
    created_at        TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    last_used_at      TIMESTAMPTZ,
    revoked_at        TIMESTAMPTZ
);
```

- 索引：`user_id`、`status` 各建一个
- Key 格式：`pxu_<32字节随机URL-safe token>`（区别于下载 key 前缀 `pxa_`）
- 存储仅保存 `key_hash`（SHA-256），明文 key 在 `POST` 响应中一次性返回，后端不留存

#### A.2 鉴权中间件

**`_require_upload_api_key()`**（用于 v1 接口）：
1. 从 `X-API-Key` header 提取原始 key
2. SHA-256 hash → 查 `data_api_keys_upload` 表（`status=ACTIVE` + `revoked_at IS NULL`）
3. JOIN `users` 表校验 `user_role = operator`（非 operator → 403）
4. 命中后 UPDATE `last_used_at = NOW()`
5. 返回 `api_key` 对象 + `user` 对象供后续使用

#### A.3 Upload API Key CRUD（Bearer Token 鉴权）

| 接口 | 方法 | 权限 | 功能 |
|------|------|------|------|
| `/data/upload-api-keys` | GET | operator | 列出当前用户所有 upload key（含 REVOKED） |
| `/data/upload-api-keys` | POST | operator | 创建 key，响应一次性返回完整 `api_key` 字符串 |
| `/data/upload-api-keys/<id>` | DELETE | operator | 撤销 key（`status=REVOKED`，记录 `revoked_at`）；仅可撤销自己的 key（`user_id` 校验），他人 key 返回 404 |

#### A.4 v1 上传接口（`X-API-Key` 鉴权）

**`POST /v1/data/upload-sessions`** — 创建上传会话：
- 参数：`task_id`、`machine_id`（7a71ba6 后可改为 `serial_number`）、`files` 列表
- 文件列表校验：
  - 解析 episode key（从文件名提取，排除 `_MANIFEST.json`）
  - manifest 完整性双向校验（缺 manifest → 400；extra manifest → 400）
- 数据库写入：插入 `data_uploads`（status=UPLOADING）+ 批量插入 `data_episodes`
- 返回：`upload_id`、`signed_urls`（GCS PUT Signed URL，TTL 由 `SIGNED_URL_TTL_SECONDS` 控制）

**`POST /v1/data/upload-sessions/<id>/resume`** — 续传：
- 校验：upload 归属（`user_id`）、状态必须为 UPLOADING、machine 归属
- 文件集合对比：与 DB 中 `expected_episode_keys` 排序比较（不一致 → 400）
- 逐文件检查 GCS：文件存在且 size 与 `size_bytes` 一致 → 跳过；否则生成新 Signed URL
- Manifest 策略：只有当对应 episode 需要上传（非 existing）时，才为 manifest 生成 Signed URL
- 响应含：`existing_files`、`missing_files`、`signed_urls`

**`GET /v1/data/uploads/<id>`** — 查询上传状态：
- 仅返回当前 API key 用户自己的 upload（`user_id` 校验，他人 → 404）
- 响应含：upload 基本信息 + `episodes` 列表（含每个 episode 的状态、路径、大小、processing_error）+ `episode_summary`

### 模块 B：Serial Number 支持（后端 `7a71ba6`）

**目标**：Operator 可在上传会话中直接使用机器序列号（`serial_number`）标识设备，无需手动查找 `machine_id`，更符合硬件侧操作习惯。

#### B.1 新增辅助函数 `_resolve_owned_machine_for_api_upload()`

```
输入：user_id + (machine_id OR serial_number)
逻辑：
  - 有 serial_number → 查 data_machines WHERE serial_number=? AND user_id=?
  - 有 machine_id  → 查 data_machines WHERE machine_id=? AND user_id=?
  - 两者均无       → 直接返回 None
输出：{machine_id, serial_number} dict 或 None
```

#### B.2 `POST /v1/data/upload-sessions` 变更

| 维度 | 旧行为（cfcc173） | 新行为（7a71ba6） |
|------|------------------|------------------|
| 必填参数 | `task_id` + `machine_id` | `task_id` + (`machine_id` 或 `serial_number`，至少一个） |
| 机器校验 | `_user_owns_machine(user_id, machine_id)` | `_resolve_owned_machine_for_api_upload()` 支持双路径查找 |
| 校验失败提示 | "machine_id is not registered to this API key owner" | "serial_number is not registered to this API key owner" |
| 缺少机器参数提示 | "task_id and machine_id are required" | "task_id and serial_number are required" |
| 响应新增字段 | — | `machine_id`、`serial_number`、`task_id` 明确返回 |

#### B.3 关键逻辑细节

- 若传入 `serial_number`，解析出 `machine_id` 后，后续数据库写入仍使用 `machine_id`（`data_uploads` / `data_episodes` schema 不变）
- `serial_number` 由 `data_machines` 表维护，确保同一用户名下唯一匹配
- 响应中同时返回 `machine_id` + `serial_number`，方便调用方建立映射缓存

### 3.2 测试类型覆盖策略

| 测试类型 | 重点覆盖场景 |
|----------|-------------|
| **接口测试（API）** | Upload Key 三种 HTTP 方法（GET/POST/DELETE）的鉴权与数据正确性；v1 上传接口的 machine_id / serial_number 双路径；resume 时文件去重逻辑 |
| **边界测试** | files 列表为空、manifest 只有多余条目、serial_number 在多用户中重名（应各自隔离）、Signed URL TTL 极限 |
| **权限测试** | 非 operator 创建 upload key；撤销他人 key；用已撤销 key 调 v1 接口；无 X-API-Key header；非 operator user_role 的 upload key |
| **数据一致性测试** | 创建会话后 DB `data_uploads` 与 `data_episodes` 记录对应；serial_number 解析后 `machine_id` 写入正确；`last_used_at` 在每次 v1 调用后更新 |
| **续传幂等性测试** | 同一文件上传两次不产生重复记录；GCS 文件存在但 size 不匹配时重新生成 Signed URL；GCS 文件存在且 size 一致时加入 `existing_files` 跳过 |
| **E2E 流程测试** | Operator 从创建 key → 识别 serial_number → 创建会话 → 上传文件 → 续传 → 查询状态的完整链路 |
| **UI 测试（Account 页）** | 两组 key 卡片同时渲染；创建 key 时一次性展示完整 key；撤销后列表移除；移动端卡片布局折叠 |
| **回归测试** | 删除旧品牌 SVG/PNG 后页面无 404 错误；OperatorSection 内机器人列表、注册按钮功能不受 VLA Foundry header 注入影响 |

### 3.3 测试环境要求

**账号矩阵**：

| 账号类型 | 用途 |
|----------|------|
| `user_role = operator`（有 machine，有 serial_number） | 核心 upload key + 上传会话测试 |
| `user_role = operator`（machine 无 serial_number） | 验证 machine_id 仍可使用 |
| `user_role = admin` 或普通用户 | 验证非 operator 创建 upload key 被拒 |
| 两个不同 operator，各有独立 machine | 验证越权撤销 key / 上传会话归属隔离 |

**数据准备**：

| 资产 | 要求 |
|------|------|
| `data_machines` 记录 | 至少 2 条属于测试 operator，其中 1 条有 `serial_number`，1 条无 |
| GCS Bucket | 需要可写入的 `DATA_RAW_BUCKET`，供续传测试 pre-seed 部分文件 |
| Upload API Key | 测试开始前通过 `POST /data/upload-api-keys` 预创建，获取完整 key |
| 合法文件集 | 至少 2 个 episode（各含 `.mcap` + `_MANIFEST.json`），用于会话创建和续传 |

## 七、cURL 调用示例

### 7.1 创建 Upload API Key（Bearer Token 鉴权）

```bash
curl -X POST https://api.prismax.ai/data/upload-api-keys \
  -H "Authorization: Bearer <your_session_token>"
```

**响应（201）**：

```json
{
  "success": true,
  "data": {
    "upload_api_key_id": 1,
    "api_key": "pxu_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx",
    "key_prefix": "pxu_xxxx",
    "status": "ACTIVE",
    "created_at": "2026-07-06T03:36:00+00:00"
  }
}
```

> `api_key` 完整值仅在此响应中出现一次，请立即保存。

---

### 7.2 创建上传会话（POST /v1/data/upload-sessions）

```bash
curl -X POST https://api.prismax.ai/v1/data/upload-sessions \
  -H "X-API-Key: pxu_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx" \
  -H "Content-Type: application/json" \
  -d '{
    "task_id": 3,
    "serial_number": "SN-TEST-001",
    "files": [
      {
        "relative_path": "episode_001.mcap",
        "size_bytes": 1048576,
        "content_type": "application/octet-stream"
      },
      {
        "relative_path": "episode_001/_MANIFEST.json",
        "size_bytes": 512,
        "content_type": "application/json"
      },
      {
        "relative_path": "episode_002.mcap",
        "size_bytes": 2097152,
        "content_type": "application/octet-stream"
      },
      {
        "relative_path": "episode_002/_MANIFEST.json",
        "size_bytes": 498,
        "content_type": "application/json"
      }
    ]
  }'
```

**响应（200）**：

```json
{
  "success": true,
  "data": {
    "upload_id": 42,
    "bucket": "prismax-data-raw",
    "upload_prefix": "raw/42/",
    "status": "UPLOADING",
    "task_id": 3,
    "machine_id": 7,
    "serial_number": "SN-TEST-001",
    "expected_episode_keys": ["episode_001", "episode_002"],
    "episode_count": 2,
    "expires_at": "2026-07-06T04:36:00.000000Z",
    "existing_files": [],
    "missing_files": [
      "episode_001.mcap",
      "episode_001/_MANIFEST.json",
      "episode_002.mcap",
      "episode_002/_MANIFEST.json"
    ],
    "signed_urls": [
      {
        "relative_path": "episode_001.mcap",
        "object_name": "raw/42/episode_001.mcap",
        "signed_url": "https://storage.googleapis.com/prismax-data-raw/raw/42/episode_001.mcap?X-Goog-Signature=...",
        "method": "PUT"
      }
    ]
  }
}
```

> **files 命名规则**：
> - `.mcap` 文件直接放根目录：`episode_001.mcap`
> - manifest 放同名子目录：`episode_001/_MANIFEST.json`
> - episode key 从文件名解析，`.mcap` 与 `_MANIFEST.json` 的 key 必须完全一一对应
> - `serial_number` 与 `machine_id` 二选一；两者同时传时 `serial_number` 优先

  -H "Content-Type: application/octet-stream" \
  --data-binary @episode_001.mcap
